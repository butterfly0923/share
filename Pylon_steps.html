What I would do: detailed to-do list

Phase 0: Define the output package first

0.1 Create one master tracker

Make a spreadsheet with one row per trace and these columns:

  • Trace name
  • API (D3D12 / Vulkan)
  • APIC package available?
  • Pylon capture available?
  • AMD GPU / driver used
  • NV GPU / driver used
  • AMD replay result (pass, fail at startup, fail mid-frame, hang, image mismatch)
  • DynamicBucketing.csv generated?
  • PI report generated?
  • NVAPI calls observed in failing run
  • Suspected blocker category
  • Can try replay flag only?
  • Needs trace/package edit?
  • Candidate standard DX replacement?
  • NV perf delta measured?
  • Final recommendation

This gives you the structure needed to answer all five boss questions with evidence instead of notes.

0.2 Define success criteria up front

For this study, count a trace as “usable on AMD” only if:

  • Pylon replay completes,
  • you can generate a PI report,
  • and DynamicBucketing.csv is present and usable for bucket timing. The PI/GIFT docs explicitly describe DynamicBucketing.csv as the report-side bucket timing metadata file.

Phase 1: Build the baseline evidence set

1.1 Normalize the current 17-trace status

For all 17 traces, gather into one folder:

  • pass/fail summary,
  • replay stdout/stderr,
  • crash logs,
  • any image diff or validation output,
  • the exact command line used,
  • GPU model and driver version.

1.2 Split the 17 traces into 4 buckets

Classify each failing trace into:

  • fails before replay starts,
  • fails during resource/pipeline init,
  • fails when issuing GPU work,
  • runs but cannot produce a valid report.

This matters because NVAPI-related failures usually cluster around replay init, extension setup, app profile handling, latency markers, AS/work-graph/ray-tracing setup, or driver-private feature calls. Pylon’s own replay options suggest these are separable axes.

1.3 Record API type first

If any trace is DX11, stop spending time on Pylon for that trace because the APIC/Pylon doc says Pylon supports only DX12 and Vulkan, not DX11.

Phase 2: Answer “Do APICs with NVAPI calls fail on AMD?”

2.1 Build a trace-level correlation table

For each of the 17 traces, create two booleans:

  • “contains NVAPI activity”
  • “fails on AMD”

Then make a simple 2x2 table:

  • NVAPI present + passes
  • NVAPI present + fails
  • no NVAPI + passes
  • no NVAPI + fails

This is your first direct answer to the APIC/Pylon question.

2.2 Use replay-flag A/B experiments to strengthen the conclusion

For each failing trace, rerun with:

  • default,
  • --no-nvapi-replay,
  • --no-nvapi-latency-marker-replay,
  • --no-app-profile,
  • optionally --nv-app-profile-via-env if profile setup itself looks suspicious. Pylon exposes all of these knobs.

Interpretation:

  • If --no-nvapi-replay turns a fail into a pass, the trace is NVAPI-sensitive.
  • If only --no-nvapi-latency-marker-replay helps, the blocker is likely not core rendering functionality.
  • If --no-app-profile helps, the issue may be profile/application registration, not rendering semantics.

2.3 Produce a concise boss-facing statement

At the end of this phase, you want one sentence like:

“APIC/Pylon traces that contain NVAPI do not universally fail on AMD, but NVAPI presence is strongly enriched among the failing set; disabling NVAPI replay converts X traces from fail to pass, which suggests replayed NVAPI behavior is a primary blocker for those traces.”

Do not claim stronger than the evidence.

Phase 3: Answer “Which NVAPI calls trigger failures?”

3.1 Extract the failing call window

For each failed replay, identify:

  • last successful call,
  • first error / exception / hang marker,
  • nearest NVAPI call before failure.

If Pylon supports diagnostic mode or driver-debug-state in your environment, enable them for a second run on the top failing traces because those options are specifically meant for replay failure diagnosis and identifying call number/state.

3.2 Group failures by NVAPI call family

Create categories rather than a flat call list:

  • app/profile calls,
  • latency marker / Reflex-related,
  • ray tracing / AS-related,
  • driver debug / diagnostics,
  • vendor-private feature enablement,
  • memory/addressing / replay object handling.

This is the form your boss will actually understand.

3.3 Rank by frequency and causality

For each NVAPI call family, label it:

  • observed near failure only,
  • strongly suspected blocker,
  • causally supported by flag A/B,
  • needs deeper owner confirmation.

That distinction is important because proximity is not proof.

Phase 4: Test your boss’s hypothesis: “Skipping those NVAPI calls may not be enough”

4.1 Explicitly run skip-only experiments

For each representative failing trace, compare:

  • default replay
  • --no-nvapi-replay
  • --no-nvapi-replay plus any other safe replay knobs you already use
  • if possible, an altered package/trace config that skips the specific feature path only

If replay passes but visuals/workload semantics become invalid, record it as:

  • “technically runs, not analytically usable.”

4.2 Validate output quality, not just survival

For every “pass after skipping NVAPI” case, verify:

  • frame renders,
  • no catastrophic corruption,
  • PI report is generated,
  • DynamicBucketing.csv exists and bucket structure is believable.

A pass that produces unusable buckets does not answer your competition need.

4.3 Separate “functional unblock” from “correct replay”

Your end table should distinguish:

  • Passes correctly
  • Passes with degraded semantics
  • Passes but loses bucket fidelity
  • Still fails

That will directly support your boss’s suspicion that “simply skipping” may not be enough.

Phase 5: Explore “Can we replace NVAPI calls with standard DX?”

Since you can patch scripts/configs but not core Pylon, your job here is mainly feasibility triage, not full implementation.

5.1 Build a replacement matrix

For each failing NVAPI family, add columns:

  • What is the NVAPI call doing conceptually?
  • Is there an obvious standard DX12 equivalent?
  • Would DX replacement preserve replay semantics?
  • Can replacement be done outside core Pylon?
  • Who owns the feature if deeper code changes are needed?

5.2 Triage into 3 classes

Class A: Likely replaceable with standard DX

  • pure metadata or optional hints,
  • latency markers / profiling markers,
  • app-profile-like behavior that has no semantic effect on rendering.

Class B: Potentially replaceable but risky

  • barrier/state/path selection that may map to DX12 but not 1:1,
  • some RT-related setup depending on whether standard DXR path exists.

Class C: Not realistically replaceable in your scope

  • vendor-private functionality with no DX analogue,
  • anything that changes hidden driver behavior,
  • anything requiring core replay/runtime changes.

5.3 Use AI only where it helps

AI can help generate:

  • candidate mapping tables from NVAPI concept → DX12 concept,
  • code search prompts,
  • pseudo-wrappers,
  • review checklists.

AI should not be trusted to assert semantic equivalence without owner review.

5.4 Pick 1–2 pilot replacements

Choose only high-leverage, low-risk candidates:

  • something common across many failed traces,
  • something with a plausible DX12 substitute,
  • something measurable on NV after replacement.

Phase 6: Measure perf delta on NV: “NVAPI vs standard DX”

This is the most decision-useful part of the study.

6.1 Pick only representative traces

Do not benchmark all 17 first. Start with:

  • 1 trace that already passes on AMD,
  • 2–3 traces that fail due to suspected NVAPI-heavy paths,
  • 1 RT-heavy / AS-heavy case if that’s a major failure mode.

6.2 Define apples-to-apples metrics

Collect on NV:

  • replay success,
  • frame time / iteration timing,
  • bucket timing from DynamicBucketing.csv,
  • optionally frame submit / finish timing from Pylon replay outputs where available. The APIC/Pylon guide shows iteration timing/perf output and saved timing CSVs from replay.

6.3 Compare three modes when possible

For each selected trace:

  • Original NVAPI path
  • Skip/disable NVAPI path
  • Standard-DX replacement path

This lets you separate:

  • “NVAPI is needed for correctness”
  • “NVAPI matters for perf”
  • “DX path is good enough”

6.4 Report perf delta in the way management wants

For each test case, summarize:

  • functional status,
  • frame-level perf delta,
  • bucket-level perf delta on the hot buckets,
  • whether the delta is acceptable for competition analysis.

A small frame-level delta with similar hot-bucket ordering may be “good enough” for your use case even if it is not exact.

Phase 7: Solve the “per-drawcall package” question properly

7.1 Align expectations with current tooling

Internally, GIFT/PIC-Perfalyze is bucket-based, and your prior thread confirms current use is bucket-level even if old naming still says “per-drawcall.”

7.2 Define what package you will actually deliver

I would package competition data as:

  • trace metadata,
  • bucket key list,
  • DynamicBucketing.csv,
  • bucket duration / cycle conversion method,
  • mapping notes to old appState or legacy flow if needed.

That is much more defensible than promising literal drawcall granularity.

7.3 If someone insists on per-drawcall

Document it as a gap, not a failure:

  • current production flow yields bucket timing,
  • not true per-drawcall timing,
  • additional tooling/work would be needed for finer granularity.

Phase 8: Turn it into a crisp final deliverable

8.1 Create a 1-page summary for your boss

Use these sections:

  • Goal
  • Dataset: 17 traces, 3 currently pass on AMD
  • Findings:
    • NVAPI correlation with failure
    • top failing NVAPI families
    • skip-only results
    • replacement feasibility
    • NV perf delta
  • Recommendation:
    • what to unblock now,
    • what to prototype next,
    • what not to pursue

8.2 Attach an appendix spreadsheet

Include:

  • per-trace evidence,
  • command lines,
  • logs,
  • replay flags tried,
  • outcome codes,
  • bucket/report status.

8.3 Make a decision table

For each failing trace:

  • Retry with flags only
  • Candidate for package/trace patch
  • Candidate for NVAPI→DX pilot
  • Not worth pursuing now

That turns your study into an execution plan.

Practical tips

  • Prioritize the 14 failures, not the 3 passes.
  • Don’t chase every NVAPI call; chase the first causally useful families.
  • Treat “runs on AMD” and “produces usable bucket timing” as separate gates.

My short recommendation

If I were you, I would focus on this exact question sequence:

  1. Which failed traces become runnable with --no-nvapi-replay?
  2. Among the remaining failures, which NVAPI families appear closest to the crash/hang point?

  4. For the optional ones, can a standard DX path preserve enough correctness?
